# GOSTYLE.md

Authoritative Go code style and project layout conventions. All code must conform — modify the code to match this file, not the reverse.

## A. Critical Constraints

### A.1 Forbidden

- A.1.a. Never invoke raw `go` commands in CI or docs when a Makefile target exists — all workflows go through the `Makefile`.
- A.1.b. Never hand-edit `/vendor/` — to patch a dependency, fork upstream or vendor it as a `replace` target.
- A.1.c. Never add `-trimpath` or other ldflags to distribution builds without updating this guide first.

## B. Architecture & File Organization

### B.1 Project Layout

- B.1.a. Flat root — `main.go` entry point, one `<name>_client.go` / `<name>_server.go` per primary struct, a `Makefile` for all workflows, `vendor/` generated by `go mod vendor` (never hand-edited).

```text
go-template/
  main.go              -- Executable entry point
  main_test.go         -- Tests for the root package
  <name>_client.go     -- One file per primary struct (db_client.go, http_client.go)
  <name>_server.go     -- Server structs follow the same pattern (http_server.go)
  go.mod               -- Root module (module app)
  Makefile             -- All build, test, lint, release workflows
  demo/
    demo.go            -- Local sub-module source
    go.mod             -- module demo
  vendor/              -- Generated by `go mod vendor`; never hand-edited
```

- B.1.b. **Local sub-modules via `replace`** — a separately-versionable package gets its own `go.mod` in a subdirectory, imported by its declared name (`import "demo"`), not a relative path. Treat it as an external dependency; the local `replace` means changes inside it need no version bump. `go mod vendor` syncs it into `/vendor` alongside external deps.

```go
// root go.mod          // demo/go.mod
require demo v0.0.0      module demo
replace demo => ./demo   go 1.26.3
```

### B.2 File-Level Layout

- B.2.a. One primary public struct per file; the file name is the struct's role in lower_snake_case (`db_client.go` → `DBClient`). Supporting types used only by that struct (small enums, helpers) go in the same file, above the primary struct.
- B.2.b. File order, top to bottom: `package`; import block (stdlib, blank line, third-party, with underscore/driver imports last); supporting types; primary public struct; `NewXxx` constructor; methods — lifecycle (`open`, `start`) first, then public API, then private helpers, then handlers.

### B.4 Dependencies & Standard Library

- B.4.a. **Imports** — two blocks separated by a blank line: standard library first, then third-party, each ordered alphabetically. Driver / side-effect-only imports use the underscore form at the end of their block. No aliases except to disambiguate same-named packages or satisfy the underscore convention.

```go
import (
    "database/sql"
    "os"

    _ "github.com/mattn/go-sqlite3"
)
```

- B.4.b. **Vendor dependencies** — `go mod vendor` materializes every direct/transitive dep (including local `demo`) into `/vendor`; builds resolve from there, not the module cache. `make deps` (`go mod tidy && go mod vendor`) is the canonical refresh, run before every `make run`/`make build`.
- B.4.c. **HTTP server via `net/http`** — handlers are methods on the server struct (not free functions), registered via `http.HandleFunc` inside `start()`. Set `Content-Type` and `Connection` explicitly before writing the body — don't rely on defaults. Default listen address is `:80`; switching to TLS is a one-line change.

```go
func (id HTTPServer) start() {
    http.HandleFunc("/", id.rootHandler)
    err := http.ListenAndServe(":80", nil)  // commented ListenAndServeTLS line for TLS
    if err != nil { panic(err.Error()) }
}

func (id HTTPServer) rootHandler(resp http.ResponseWriter, req *http.Request) {
    defer req.Body.Close()
    resp.Header().Set("Content-Type", "text/html")
    resp.Header().Set("Connection", "close")
    resp.Write([]byte("<head></head><body><h2>OK</h2></body>"))
}
```

- B.4.d. **Database via `database/sql`** — a driver registered via underscore import; `DBClient` wraps a single `*sql.DB`, exposing lowercase `exec`/`query` methods (the stub `query` drives `rows.Next()`/`rows.Scan()` and returns a flat `[]string` — real callers write a typed equivalent). Prefer the pure-Go driver `modernc.org/sqlite` (builds with `CGO_ENABLED=0` → clean static binaries); fall back to CGO `github.com/mattn/go-sqlite3` only when a CGO-only feature is genuinely required (it breaks static builds), keeping both lines in `db_client.go` with the CGO one commented.

```go
import _ "modernc.org/sqlite"                 // default — pure Go, note "sqlite"
db, err := sql.Open("sqlite", dbFile)
import _ "github.com/mattn/go-sqlite3"         // fallback — CGO, breaks static builds
db, err := sql.Open("sqlite3", dbFile)
```

## C. Code Construction & Logic

### C.1 Logic Layout & Readability

- C.1.a. **Struct-as-namespace** — all behavior is namespaced on structs; no free-standing exported functions other than `NewXxx` constructors. A struct is both data container and namespace. Fields are declared before methods. Every method receiver is named `id` regardless of type — a deliberate, uniform convention that keeps method bodies grep-friendly.

```go
type DBClient struct {
    db *sql.DB
}

func (id *DBClient) open(dbFile string) { ... }  // mutating  → pointer
func (id HTTPServer) start()            { ... }  // stateless → value
```

- C.1.b. **Pointer vs value receivers** — mutating methods take `*T`, pure/read-only/dispatch methods take `T`. A type must be consistent — don't mix receiver kinds on one struct without clear reason (`DBClient` mutates `db`, so all its methods are `*DBClient`).
- C.1.c. **Constructor pattern** — every primary struct has a `NewXxx` constructor returning the struct by value (the caller decides whether to take the address, preserving zero-value semantics). When construction needs heavy work (opening files, dialing connections), the constructor builds the zero value then calls a separate lifecycle method (`open`/`load`/`start`) taking `*T` so it can mutate and stays independently callable.

```go
func NewDBClient(dbFile string) DBClient {
    client := DBClient{nil}
    client.open(dbFile)
    return client
}
```

### C.2 Naming Conventions

| Element       | Convention             | Example                          |
| ------------- | ---------------------- | -------------------------------- |
| Package       | lowercase, single word | `main`, `demo`                   |
| File          | lower_snake_case       | `db_client.go`, `http_server.go` |
| Struct        | PascalCase             | `DBClient`, `HTTPClient`         |
| Constructor   | `New<Struct>`          | `NewDBClient`, `NewHTTPServer`   |
| Method        | lowerCamelCase         | `open`, `exec`, `rootHandler`    |
| Receiver name | `id` (always)          | `func (id *DBClient) ...`        |
| Field         | lowerCamelCase         | `db`, `maxRetries`               |
| Constant      | PascalCase or ALL_CAPS | `Version`, `MAX_RETRIES`         |
| Acronym       | preserve case          | `DBClient`, `HTTPServer`, `URL`  |
| Test function | `Test<Subject>`        | `TestFoo`, `TestDBClient_Query`  |

- C.2.a. Acronyms keep their case — `DBClient` not `DbClient`, `HTTPServer` not `HttpServer`, `URL` not `Url`.

### C.4 Error Handling & Guard Clauses

- C.4.a. Methods that can fail return `(T, error)`; methods that can't return only `T`. Don't add a sentinel error when the standard `error` interface suffices.
- C.4.b. Template stubs `panic(err.Error())` as deliberate scaffolding — when adapting for real use, replace each panic with a proper error return.

```go
result, err := id.db.Exec(sql)
if err != nil { panic(err.Error()) }  // stub only
if err != nil { return nil, err }     // production
```

## D. Systems & State Management

### D.2 Resource Management

- D.2.a. Pair resources with `defer` at acquisition. HTTP handlers always `defer req.Body.Close()` even though the server frees it eventually.

```go
resp, err := http.Get(url)
if err != nil { panic(err.Error()) }
defer resp.Body.Close()
```

## E. Quality, Tooling & Frontend

### E.3 Build, Tooling & Task Runners

- E.3.a. All workflows go through the `Makefile`.

| Target                  | Purpose                                          |
| ----------------------- | ------------------------------------------------ |
| `make` / `make run`     | `go mod tidy && go mod vendor && go run .`       |
| `make build`            | Same deps, then `go build .`                     |
| `make test`             | `go test -v -count=1 .` (cache-busted)           |
| `make lint`             | `go vet`                                         |
| `make format`           | `go fmt`                                         |
| `make dist`             | `CGO_ENABLED=0` strip-flags build (~40% smaller) |

- E.3.b. Run a single test: `go test -v -run TestFoo .`. The `-count=1` in `make test` disables Go's result cache so tests always re-run.
- E.3.c. **Strip flags** — distribution builds use `--ldflags "-s -w"` (`-s` strips the symbol table, `-w` drops DWARF debug info). Combined with `CGO_ENABLED=0` this yields the smallest static-friendly binary.
- E.3.d. **Release** — `make release` zips source + metadata and publishes via `gh release create`. Edit the `VERSION`, `PROJECT`, and `REPO` variables at the bottom of the Makefile per fork before the first release — don't script around them.

### E.4 Testing Standards & Test Data

- E.4.a. Tests live in `*_test.go` alongside their source, in the same package (`package main` for root) — no separate `tests/` directory or external `_test` package unless cross-package isolation is genuinely needed. Use the standard `testing` package with `t.Fatalf` for assertions; keep structure minimal. There's no fixture loader or mocking framework — the `New` patterns make real dependencies (a SQLite file, an HTTP server on a free port) cheap to spin up directly per test.

```go
func TestFoo(t *testing.T) {
    if !ok { t.Fatalf("Foo test failed") }
}
```

- E.4.b. Test names are `TestXxx` matching the unit (`TestDBClient_Query`, `TestHTTPServer_RootHandler`). Reserve `TestMain(t *testing.T)` for a smoke test of `main()` — note Go separately recognizes `TestMain(m *testing.M)` (different signature) for setup/teardown.
